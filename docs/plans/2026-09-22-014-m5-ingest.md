### Drift check result (run at `9caca27b`, 2026-09-22, M5 executor)

Plan 003 is **IMPLEMENTED**; M1.5, M2 and the M4 core are merged. The approach holds; these refinements were
verified against the live code before coding:

- **Pipeline entry points.** `FileTranscriptionPipeline.importFile(from:sourceType:audioTrackOrdinal:)` copies a file
  into `media/<id>/source.<ext>` and inserts a `.processing` row; `process(id:)` / `retry(id:)` run it. Link downloads
  land a file first, then call the unchanged `process(id:)`. `TranscriptionJobCenter` (M1.5) tracks jobs, progress
  (`JobProgress(stage:fraction:)`, `PipelineStage`) and one continued-processing request per user action; link and
  document jobs join it through one additive "track an existing row" entry point.
- **Documents are `Transcription` rows** (`sourceType: .document`, text in `rawTranscript`, no words, no media
  player). M4's `DeliverableService` reads `displayText` / `TranscriptPromptFormatter.timestampedText` (which falls
  back to `displayText` without segments), so every template works on a document with no M4 change.
- **Schema.** Existing migrations are `v1`…`v4`; the M3 lane adds `v5-meetings`. M5 adds **`v6-documents`**: nullable
  `sourceURL` (the pasted link), `sourceTitle` (episode, video or document title), `documentFormat`, and
  `documentPages` (JSON, per-page text and whether it came from the text layer or OCR). `displayTitle` becomes
  `titleOverride ?? sourceTitle ?? derivedTitle ?? fileName`. The store protocol does not change (writes go through
  `insert` and `savePreservingUserMetadata`), so other lanes' fakes keep compiling.
- **New module `ChirpIngest`** (depends on `ChirpCore` only): link classifier, podcast lookup and feed parser (ports),
  the resumable downloader, YouTube captions, and document text extraction (PDFKit, Vision, `NSAttributedString`,
  DOCX). `ChirpFeatures` orchestrates (`LinkIngestService`, `DocumentImportPipeline`, `LinkImportViewModel`).
- **DOCX without a new dependency.** Foundation on iOS has no public unzip API, but `NSData.decompressed(using: .zlib)`
  inflates raw DEFLATE; a ~150-line ZIP central-directory reader covers `word/document.xml`. So ZIPFoundation is not
  added and THIRD_PARTY_LICENSES gains nothing.
- **Downloads** go to `media/<id>/download.part` (with a small `download.part.json` holding the URL and validator),
  resume with `Range` + `If-Range` on Retry when the server allows, and become `media/<id>/source.<ext>` only when
  complete. A new `PipelineStage.downloading` shows real byte progress on the row.
- **Share sheet.** M1.5 declares `public.audio` and `public.movie`; M5 adds PDF, plain text, Markdown, RTF, HTML and
  DOCX document types, and `AppEnvironment.openIncoming` routes them to the document path (the Inbox copy is still
  deleted once the import settles).
- **YouTube audio stays out of scope** until the owner decides (STOP condition); the options are written below.
- **App shell is shared with M3 and M4-UI lanes.** New screens go in new files (`PasteLinkSheet`, `DocumentScreen`,
  `DocumentRow` pieces); shared files get small additive edits only (the Paste-a-link tile, `AppEnvironment`,
  `LibraryScreen` row and destination, `project.yml`, `IncomingFileInbox`).

## Steps

### Step 1: Link classifier and download manager

Classify a pasted or shared URL: Apple Podcasts episode, podcast feed, direct media (by extension or content type),
YouTube, other (unsupported with a clear message). Downloads use `URLSession` with progress into the item's media
folder, cancellable, resumable where the server allows. Downloads never occupy a speech-scheduler slot.

**Verify:** classifier table tests; download tests against a local `URLProtocol` stub (no real network in tests).

### Step 2: Apple Podcasts

Port upstream: `https://itunes.apple.com/lookup?id=<showId>&entity=podcastEpisode&limit=200`; match the `?i=` episode
id from the share link against `trackId`; fall back to the RSS feed. Then import the downloaded file with
`sourceType: .podcast`.

**Verify:** resolver tests with recorded JSON fixtures (synthetic, no personal data); device: paste a real episode.

### Step 3: YouTube, captions first

Port the youtube-transcript-api method: watch page → `INNERTUBE_API_KEY` → `/youtubei/v1/player` as the `ANDROID`
client → caption track `baseUrl` → timed text. Store as a `url` item with segments from caption timing (no audio
player). If there are no captions, say so and offer Share/import of a file the user has.

**Before any YouTube audio download:** write the options and the terms-of-service note in the PR/hand-off and get
the owner's decision. If approved, add YouTubeKit (verify its license) in `.local` mode only (never its remote
fallback server), behind a Settings toggle, off by default.

#### YouTube audio: decided (owner, 2026-09-22) — option C, the Mac companion

**Decision (owner, 2026-09-22):** YouTube audio comes from the owner's Mac through the Parakeet companion's yt-dlp
(option C below; [ADR-014](../../spec/adr/014-mac-companion.md), built in [plan 019](2026-09-22-019-mac-companion-and-m5-finish.md)).
App Review is irrelevant: Parakeet is never submitted. YouTube's terms still forbid automated download; the owner
accepts that for personal use. The table below is kept as the record of the options.

#### The options as written for the owner (before the decision)

Captions are built (`YouTubeCaptionFetcher`, `LinkIngestService.importCaptions`). **No YouTube audio is downloaded.**
When a video has no captions, the app says so and suggests sharing a file the owner already has. The options for
audio, for the owner to choose from:

| Option | What it takes | Works when | Cost and risk |
|---|---|---|---|
| **A. Captions only** (built) | Nothing more | The video has captions (manual or automatic) | Fails without captions; YouTube can change its internal API (the client is small, its errors say so) |
| **B. YouTubeKit on the phone** | Add YouTubeKit (MIT per its repository; verify before adding) in `.local` mode only, AAC itag 140, behind a Settings toggle, off by default, then the normal download → transcribe path | Most public videos | Breaks every few weeks when YouTube changes; must never use its `.remote` fallback (a third-party server); an App Store or TestFlight build would likely be rejected (App Review guideline 5.2.3); treat like ADR-010: personal builds only |
| **C. The owner's Mac as a trusted helper** | A small LAN endpoint on the Mac running MacParakeet's bundled yt-dlp; the phone sends the link, fetches the audio file | The Mac is on and on the same network | Most robust downloader; the link leaves the phone only to the owner's own machine; needs a Mac-side service (M7/M8 scope) |
| **D. Share or import the file** (built, M1/M1.5) | Nothing | Always, for media the owner already has | Manual step |
| E. Capture a web view's audio | Not possible: iOS gives apps no audio capture of `WKWebView` playback | Never | Rejected |

**Terms of service.** YouTube's terms forbid downloading content "except as expressly authorized by the Service"
and accessing the service "using any automated means". Fetching captions through the player API is also automated
access, so option A already relies on the owner's acceptance for personal use. Personal, sideloaded use lowers the
exposure but does not change the terms. App Review guideline 5.2.3 bars apps that download media from third-party
sources such as YouTube without authorization, which matters only if Parakeet is ever distributed.

**Recommendation:** keep A and D; if audio is needed, prefer C (a maintained yt-dlp on hardware the owner controls);
choose B only for personal builds, behind the toggle, knowing it needs frequent updates. Record the decision here
before any of B or C is built (STOP condition).

### Step 4: PDF

`PDFDocument` text per page; pages without text are rendered to images and read with Vision
`RecognizeDocumentsRequest` (iOS 26). Result: a `document` item with page-numbered text.

**Verify:** tests with generated PDFs (text and image-only pages created at test time).

### Step 5: Text documents

TXT and Markdown as UTF-8; RTF and HTML via `NSAttributedString`; DOCX by unzipping (ZIPFoundation) and reading
`word/document.xml` paragraphs. Result: `document` items.

**Verify:** fixtures generated at test time; malformed files fail with a clear error.

### Step 6: UI

Paste a link sheet (paste button, detected type, progress, errors); document rows in Library with a document cover;
a document detail view (text, no player) that M4 templates can use.

Steps ran in the orchestrator's priority order (1, 2, PDF, text, YouTube, UI). Decisions made while executing:

- **Documents are `Transcription` rows** (no new table): M4 templates, search, favorites, privacy and delete work
  unchanged. Only `v6-documents` columns were added; the store protocol is untouched.
- **HTML without `NSAttributedString`**: its HTML import must run on the main thread and loads WebKit; a small
  converter keeps structure and fetches nothing. RTF still uses `NSAttributedString`; its title comes from the RTF
  `\info` group because the title attribute is macOS-only.
- **Downloads land in the item's folder** (`download.part` + `.json`), and the system progress gives a download the
  first 15% of a link job (`JobProgress.overallFraction`), so it never goes backwards when transcription starts.
- **Unknown download size**: the row shows "Downloading · 0%" until the end (no fraction is invented); podcast hosts
  normally send `Content-Length`.
- **Shared plain text of any extension** (`.log`, `.csv`, source) is read as plain text rather than failing in the
  audio pipeline.
- **Capture edits beyond the tile**: the Recent list and navigation use `LibraryItemRow` / `LibraryItemScreen` so a
  document opens its own screen (one-token swaps), plus a DEBUG-only launch hook (`IngestPreviewLaunch`) used for the
  screenshots.

### Open items closed by plan 019 (lane L1, 2026-09-22)

- **YouTube audio**: decided (above) and built. When a video has no usable captions and a Mac companion is set up,
  the Paste a link sheet offers "Get the audio from your Mac"; the person confirms once per link that the link goes to
  their Mac; the audio comes back into `media/<id>/source.m4a` and is transcribed on the phone. Without a companion the
  message says how to set one up.
- **Unknown download size**: `JobProgress.isIndeterminate` — the row and the sheet show "Downloading…" with a spinner,
  never "0%" (`CompanionIngestTests.testUnknownSizeDownloadIsIndeterminateAndNeverZeroPercent`,
  `CompanionScreenLogicTests`).
- **YouTube client version**: youtube-transcript-api still uses ANDROID `20.10.38` (master and release v1.2.4,
  checked 2026-09-22); it is now one constant, `YouTubeCaptionFetcher.innertubeClient`.
- **Live services**: `LiveIngestTests` (opt-in, `CHIRP_LIVE_NETWORK_TESTS=1`) ran once from the Mac on 2026-09-22.
  First run: the podcast test **passed** (a current "Up First" episode link resolved to https audio with a duration);
  the captions test **failed** with `pageChanged` — YouTube redirects Parakeet's own User-Agent to m.youtube.com's
  "unsupported browser" page, which has no `INNERTUBE_API_KEY`, so **captions could not have worked on the phone**.
  Fix: every YouTube request now sends youtube-transcript-api's User-Agent (`YouTubeCaptionFetcher.userAgent`,
  asserted in `YouTubeCaptionFetcherTests`). Second run: **both passed** ("Tears of Steel": 76 manual English cues,
  734 s).
