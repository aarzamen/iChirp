# R5 review: ChirpFeatures flows (Dictation, Meeting, Create, Voice, Structure)

Commit `53bc2cc6` on `main`. Read-only review. Nothing was built or run.

## Overall assessment

Each flow is solid on its own. The dictation state machine uses a generation token to drop stale completions. The meeting writes its lock before any audio, records to a crash-readable CAF and sends recorder commands through one ordered chain. Store writes are field-level, voice routing re-reads the item's class before every chunk, and every log line in scope holds ids, counts and error types only. The weak points are where two features meet:
- dictation started from a Clinical Create chain (the row is Personal until the chain catches up);
- voice commands versus the saved record ("send to SOAP" reads the text that still holds the "scratch that"-ed order);
- recorder failures versus coordinator state (Resume after a full disk shows Recording while nothing is written);
- dictation's crash path, which never took the meeting crash-format lesson (a killed WAV reads as 0 s).

The tests miss these cases because their fakes ignore file contents and recorder internals.

### R5-1 [high] [privacy] Create → Speak with Clinical stores the dictation as Personal until the chain catches up; a kill makes it permanent, and "read back" can route the first chunk as Personal
- **Where:**
  - `ChirpKit/Sources/ChirpFeatures/Dictation/DictationCoordinator.swift:413-421`: the row is inserted with no class, so `Transcription`'s default `.personal` (`ChirpCore/Models/Transcription.swift:81`).
  - `DictationCoordinator.swift:636-639`: orphan adoption also uses the default class.
  - `ChirpKit/Sources/ChirpFeatures/Create/CreateFlow.swift:328-331, 365-369`: the class is raised only after `recordSpeech()` returns `.saved`.
  - `App/Sources/Create/AppEnvironment+Create.swift:63-88`: `dictation.start()` gets no class.
  - `ChirpKit/Sources/ChirpFeatures/Dictation/DictationVoiceCommands.swift:180-184`: read back is launched from `finalize()` (`DictationCoordinator.swift:496-498`) *before* `send(.transcriptionCompleted)` (`:505`).
  - `App/Sources/AppEnvironment.swift:336-343`: the relay reads the class as stored at that moment.
  - The guarantee is promised in `ChirpKit/Sources/ChirpFeatures/Create/CreateRecipe.swift:12-13` ("A clinical recipe makes its item clinical from the first write") and in its VoiceOver `spokenDescription` ("marked clinical from the start").
- **Problem:** Link, file and text inputs are created with the chosen class (review I1). Speak cannot be, because `DictationCoordinator` has no way to receive the class. Anything that happens to the row before `recordSpeech` returns sees it as Personal.
- **Failure scenario:**
  - **Kill.** A "Dictate → SOAP note" recipe with Clinical on. iOS ends the app during the final pass (`.processing` row) or while recording (an orphan WAV). At relaunch, `markStaleProcessingAsInterrupted` or `recoverOrphanedRecordings` leaves an Interrupted row with class **Personal**, and the chain is gone. The physician later retries it from the Library and runs Summary on a cloud model. `DeliverableService` routes it as Personal, so no clinical question is asked and PHI leaves the phone.
  - **Race.** Voice commands on, a Grok (cloud) voice, and "Read back." said in a clinical Create dictation. The read-back Task can pass its first `checkRoute` with Personal before `applyPrivacyClass` commits, sending up to 500 characters before the per-chunk re-check stops it.
- **Fix:**
  - Add `DictationCoordinator.start(privacyClass:)` and insert the row with that class.
  - Persist the requested class in the recording folder (for example a small marker file next to `dictation.wav`) so orphan adoption uses it; adopt an orphan of unknown class as `.clinical`, the "unknown reads as clinical" rule `VoiceSourcePrivacy` already uses.
  - Give read back the same `.clinical` floor that command words get (`DictationVoiceCommands.routingClass`).
  - **Tests:** a `CreateFlowTests` case whose `recordSpeech` fake inserts the row and asserts it is `.clinical` at insert; an orphan-adoption test with the marker.
- **Confidence:** CONFIRMED for the kill paths (traced). PLAUSIBLE for the read-back race (timing-dependent).

### R5-2 [high] [clinical safety] "Send to SOAP" / "Send to Transform" run on the stored verbatim transcript, so a "scratch that"-ed order reaches the SOAP note
- **Where:**
  - `DictationCoordinator.swift:491-498`: commands are applied to the clipboard copy only.
  - `DictationCoordinator.swift:569-582`: the row keeps the raw and clean text, and its segments are built from the raw words.
  - `DictationVoiceCommands.swift:187-190`: the pending Transform carries only the transcription id.
  - `App/Sources/Screens/Structure/DictationVoiceCommandViews.swift:102-106`: `SOAPFromFieldsSheet(transcriptionID:…, notes: "")`.
  - `ChirpKit/Sources/ChirpText/TranscriptPromptText.swift:14-29`: model input is the segment text, which comes from the raw words.
  - `DictationCoordinatorTests.swift:143-144` pins "the saved transcript keeps every word".
- **Problem:** The copy is the final pass with commands applied. The action the same dictation asks for ("Send to SOAP") runs the template on the stored record instead, and that record still holds the scratched sentence and the command words. Extract fields is protected (`CrossSentenceCorrection` treats "scratch that" as a cue); the SOAP template run is not.
- **Failure scenario:** The physician dictates "Start amoxicillin 500 mg p.o. TID. Scratch that. Start azithromycin 250 mg daily. Send to SOAP."
  - The clipboard gets "Start azithromycin 250 mg daily."
  - The SOAP sheet opens on the transcript, whose prompt is "[00:00] Start amoxicillin 500 mg p.o. TID. Scratch that. Start azithromycin 250 mg daily. Send to SOAP."
  - The on-device model can put amoxicillin in the Plan, while the physician believes it was removed.
- **Fix:** Pass the copied (commands-applied) text to the send-to run, either as the run's source or as `userNotes` stating it supersedes the transcript. Alternatively, store it as a derived text that deliverable input prefers for dictations.
- **Test:** a fake `LanguageModel` captures the prompt; "scratch that" followed by "send to SOAP" must never send the scratched sentence.
- **Confidence:** CONFIRMED.

### R5-3 [high] [data loss / honest UI] Meeting: after a disk-full write failure, Resume shows "Recording" but nothing is ever written again
- **Where:**
  - `ChirpKit/Sources/ChirpFeatures/Meeting/MeetingCoordinator.swift:391-394`: `.failed` goes to `.waitingForResume`.
  - `MeetingCoordinator.swift:187-188, 405-413`: `restartMicrophone` treats a successful `resume()` as "recording again".
  - `ChirpKit/Sources/ChirpAudio/Capture/MeetingRecorder.swift:183, 192-204`: `writeFailed` is sticky.
  - `ChirpKit/Sources/ChirpAudio/Capture/SharedMicrophoneStream.swift:153-159`: `resume()` does nothing when the engine is running.
  - `App/Sources/Screens/Meeting/MeetingScreen.swift:220-223, 450-451`: the full-disk notice is shown with a Resume button.
- **Problem:** A write failure is not a microphone failure, but it reuses the microphone state, whose action is Resume. Resume succeeds without doing anything, the coordinator returns to `.recording`, and the writer keeps dropping every buffer.
- **Failure scenario:**
  1. During an hour-long meeting the disk fills. The screen says "…Everything up to now is saved. Stop to transcribe it." and offers Resume.
  2. The person deletes some photos and taps Resume.
  3. `captureProblem` becomes nil, the state is `.recording`, the source line reads "Microphone · saving on this iPhone", and the Live Activity shows Recording with a running timer.
  4. `MeetingAudioWriter.process` returns early forever. The rest of the meeting is silently lost; only the in-app timer and meter freeze.
- **Related:** the dictation writer logs and drops failed writes with no event (`DictationRecorder.swift:168-173`). The dictation keeps showing Recording with a frozen timer, and the final transcript has an unannounced gap.
- **Fix:** Give a write failure its own state (for example `.storageFull`) whose only action is Stop & save. Alternatively, make `MeetingRecorder.resume()` clear `writeFailed` only after a test write succeeds, and throw otherwise. Surface dictation write failures as a capture event.
- **Test:** the writer fails, then `resume()` must not return to `.recording` unless audio is being written.
- **Confidence:** CONFIRMED.

### R5-4 [high] [data loss] A dictation killed while recording is adopted with "Retry", but its WAV reads as 0 s, so Retry says "Didn't catch that" and suggests deleting it
- **Where:**
  - `DictationCoordinator.swift:625-651`: adoption, with the message "Retry to transcribe what was kept".
  - `ChirpKit/Sources/ChirpAudio/Capture/DictationRecorder.swift:146-160`: `AVAudioFile` WAV.
  - The repo's own measurement: `docs/research/2026-09-22-meeting-crash-format.md:27, 30-31` ("a killed dictation's WAV holds the samples but reads as 0 s until its header is repaired").
  - No header repair exists anywhere in `ChirpKit/Sources` (grep).
  - The engines read with `AVAudioFile`, for example `ChirpEngineFluidAudio/ParakeetEngine.swift:319, 378`.
  - The empty-transcript message is at `DictationCoordinator.swift:608-611`.
- **Problem:** Meetings moved to CAF because of this exact measurement. Dictation kept the WAV and the adoption promise.
- **Failure scenario:**
  1. A 3-minute clinical dictation is started with the Action Button from another app, and iOS kills Parakeet under memory pressure.
  2. At relaunch the Library shows it as Interrupted: "Retry to transcribe what was kept".
  3. Retry opens a file with 0 frames, so `emptyTranscript` follows: "Didn’t catch that — no speech was recognized. Retry, or delete this dictation."
  4. The samples are on disk but unreachable, and the screen invites deleting them.
- **Why the test passes:** `DictationCoordinatorTests.swift:395-419` passes only because the fake engine ignores the file's contents.
- **Fix:** Before adopting, rewrite the RIFF size and data-chunk size from the file length, or record dictation as CAF like meetings.
- **Test:** write through `RecordingWriter`, copy the file *before* `close()` (what a kill leaves), adopt it, and assert `AVAudioFile` reads the expected frame count.
- **Confidence:** CONFIRMED (code plus the repo's own research).

### R5-5 [medium] [honest UI] MeetingFinalizer reports every normalization failure as "No audio was saved for this meeting (it stopped within the first moment)"
- **Where:**
  - `ChirpKit/Sources/ChirpFeatures/Meeting/MeetingFinalizer.swift:165-171`: catch-all mapped to `FinalizeError.noAudio`; the message is at `:33-34`.
  - The message is shown by `MeetingCoordinator.swift:519-524` beside "The recording and your notes are kept" (`MeetingScreen.swift:365-366`).
- **Failure scenario:** A 2-hour meeting finishes with about 350 MB free. Normalization needs about 230 MB per hour for the 16 kHz WAV, so it fails with a disk-full `readerFailed`. The row is marked `.failed` with "No audio was saved… (it stopped within the first moment)". The person can believe the recording is empty and delete a recoverable 2-hour meeting. A decode error after a crash is mislabeled the same way, and the normalizer's own sentence is thrown away.
- **Fix:** Map only the empty-file cases (`noAudioTrack`, or zero samples) to `noAudio`. For anything else, say "The recording is saved. <normalizer message>. Tap Retry."
- **Test:** a normalizer fake throwing `readerFailed("…")` must give a message that does not contain "No audio".
- **Confidence:** CONFIRMED.

### R5-7 [medium] [data integrity] With "Keep dictation audio" off, the WAV is deleted before the transcript is saved; a failed save loses both
- **Where:** `DictationCoordinator.swift:586-592` (the delete), then the save at `:592`, the failure at `:594-598`, `markFailed` at `:606-616`, and Retry hitting `sourceFileMissing` at `:545-547`.

### R5-8 [medium] [data integrity] Transcript Notes: a failed load leaves the editor live, and the next keystroke autosaves over the stored meeting notes

### R5-9 [medium] [correctness] Edit by voice rewrites the stored text, not the unsaved draft on screen, and the result is then hidden behind that stale draft
- **Where:**
  - `ChirpKit/Sources/ChirpFeatures/DeliverableService.swift:758` (`let source = document.text`) and `:796` (append with no expected-base check; see `ChirpStore/DeliverableVersionStore.swift` `appendDeliverableVersion`).
  - `App/Sources/Screens/Transforms/DeliverableDetailScreen.swift:193-195` opens the sheet even with unsaved changes; the reload is at `:259-264`.
  - `ChirpKit/Sources/ChirpFeatures/DeliverableLibraryViewModel.swift:101-103` keeps the draft on reload.
- **Failure scenario:**
  1. The person hand-edits a SOAP note without saving and says "make it shorter".
  2. The model shortens the *stored* text, without the hand edits, and a new version is saved.
  3. `load()` keeps the stale draft on screen, so the voice edit seems to have done nothing.
  4. Tapping Save writes the stale draft over it; the voice edit survives only in Versions.
- **Fix:** Save or ask before opening Edit by voice when `hasUnsavedChanges`. Alternatively, edit the draft and give `appendDeliverableVersion` an expected base text (compare-and-swap).
- **Test:** draft differs from the stored text; check which text the edit uses and what is shown after it.
- **Confidence:** CONFIRMED.

### R5-11 [low] [Live Activity] Updates are fire-and-forget Tasks with no ordering, and dictation's "waiting for Resume" wording is wrong
- **Where:** `App/Sources/Support/DictationLiveActivity.swift:25-26, 45, 65`; `App/Sources/Support/MeetingLiveActivity.swift:28-29, 48, 68`.
- **Problem:**
  - Each `show`/`end` starts its own `Task { await activity.update(...) }`. This is the bug class from `docs/solutions/concurrency/order-sensitive-commands-need-one-chained-task.md`: a quick Pause → Resume, or an interruption followed by auto-resume, can leave the Lock Screen showing Paused while recording.
  - Dictation in `.paused(.waitingForResume)` says "A call or Siri has the microphone" after the call has ended. Meeting says "Open Parakeet and tap Resume".
- **Fix:** Chain the updates through one tail task, as `sendToRecorder` does, and map `waitingForResume` to its own wording.
- **Confidence:** PLAUSIBLE (ordering), CONFIRMED (wording).
