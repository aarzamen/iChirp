# R8 — Repository hygiene: scripts, build config, CI, Mac companion, docs consistency, test-suite quality

Reviewed: `main` @ 53bc2cc6 (read-only). Method: read every `scripts/*.sh` and stub server, `project.yml`, tracked
`Config/*`, `.github/workflows/ci.yml`, all of `companion/` (source, tests, pyproject, lock), the docs named in the brief
plus spec/03, spec/06, spec/10, module READMEs; `/bin/bash -n` (bash 3.2.57) on every script; a read-only relative
link checker over 111 tracked `*.md` files (scratchpad `linkcheck.py`); a heuristic assertion-free-test scan; `git`
branch/merge inspection; read-only `gh` queries of the latest CI runs and repo security settings.

## Overall assessment

Hygiene is better than average for a solo project: every script parses under macOS bash 3.2 with `set -euo pipefail`
and no bash-4 features, device scripts never pass provisioning flags and refuse to guess the phone when they write data,
the companion's token guard is constant-time and covers every route except health, its link allowlist and
no-content logging are tested, `.gitignore` covers everything in `git status --ignored`, and no secrets or PHI are
tracked (the `sk-ant-…` strings in tests are synthetic `TESTKEY`/`NEVERINDEFAULTS` values). The real problems are
signal quality and drift: CI on `main` HEAD is red from a race in a benchmark test (code identical to the last green
run), `run_device.sh` labels almost any build failure a signing failure, and the agent- and owner-facing docs
(AGENTS.md §1, README status, plans board, QA-guide preconditions, distribution.md) describe a repository several
weeks younger than the code. The privacy-enforcing app-hosted tests and the companion's tests run nowhere
automatically, GitHub secret scanning is off on this public repo, and the microphone permission text over-promises
given that recordings are in device backups. No critical findings.

### R8-1 [high] [ci/tests] — CI is red on `main` HEAD: a race in `ASRBenchmarkTests.testPeakMemoryIsTheHighestSampleDuringTheRun`
- Where: `ChirpKit/Tests/ChirpFeaturesTests/ASRBenchmarkTests.swift:126-136`; `ChirpKit/Sources/ChirpFeatures/Benchmark/ASRBenchmark.swift:271,281-282,325-334`
- Problem: the fake `memory` reader returns a value derived from a shared call counter (`samples.values.count % 5 * 10 + 50`), but three readers consume it during the first pass (`load: true`): the outer `sampler`, `footprintBefore = memory()` and the inner `loadSampler`. The test compares `peakMemoryBytes` (outer sampler only) with the max over **all** reads. Whenever the read that returns 90 goes to the load sampler or to `footprintBefore`, the outer peak is 80.
- Failure scenario / evidence: GitHub Actions run 36942765664 on 53bc2cc6 (2026-10-01): `ASRBenchmarkTests.swift:136: XCTAssertEqual failed: ("Optional(80)") is not equal to ("Optional(90)")`, `Executed 1615 tests, with 20 tests skipped and 1 failure`. The last green run (84d06ceb) differs from 53bc2cc6 only in `.gitignore`, `AGENTS.md`, `CLAUDE.md`, `APPLE_DEVELOPER_WARNING.md`, `spec/README.md` — zero code change, so this is a flake, and the public CI status of `main` is now failing. (It also contradicts spec/09-testing.md:11 "Tests are deterministic".)
- Fix: give the test a reader whose answer does not depend on how many other readers ran, e.g. return 90 only while a flag set inside the fake engine's `transcribe` is on (50 otherwise) and hold `transcribe` until the outer sampler has read at least once more (`waitUntil`), then assert `peakMemoryBytes == 90`. Re-run the class repeatedly (`swift test --filter ASRBenchmarkTests` in a loop) before merging.
- Confidence: CONFIRMED

### R8-2 [high] [scripts] — `run_device.sh` prints "Signing failed … open Xcode" for almost any build failure
- Where: `scripts/run_device.sh:72-81` (regex at :78), `:214-216`; `project.yml:162-168` (widget stamp phase, `basedOnDependencyAnalysis: false`); `docs/human-qa-guide.md:32`
- Problem: `fail_with_log` greps the whole xcodebuild log, case-insensitively, for `signing|…|certificate|CodeSign|…`. A non-quiet device build log always contains the environment dump of the widget target's "Stamp Build Identity" script phase (`export CODE_SIGNING_ALLOWED=YES`, `CODESIGNING_FOLDER_PATH`, `CODE_SIGN_CONTEXT_CLASS`, …), and that phase runs on every build, before the app target's phases.
- Failure scenario / evidence: in this Mac's own `.build/device-logs/xcodebuild-device.log`, the first `PhaseScriptExecution Stamp\ Build\ Identity …/iChirpWidgets.build` is at line 229 and `export CODE_SIGNING_ALLOWED\=YES` at line 320, before the app target's phase at line 893. So a Swift compile error in `App/Sources` ends with the compile errors followed by "Signing failed. Do NOT try to fix the Apple Developer account from a script. Open iChirp.xcodeproj in Xcode once … build to the iPhone from the Xcode GUI, then rerun." The QA guide tells the owner "If the script prints a signing message, follow it" — he goes into the Xcode signing flow for a code error.
- Fix: classify only real error lines, e.g. `grep -E 'error:' "$log" | grep -qiE 'provisioning profile|No profiles for|No Account for Team|signing certificate|requires a development team|Code ?Sign(ing)? (error|failed)|errSecInternalComponent'` → signing advice; otherwise "Build failed — see the errors above". Keep a small fixture log (compile error with the env dump) and a check that it is not classified as signing.
- Confidence: CONFIRMED that the regex matches the env dump and that the dump precedes the app target in a real log; the compile-error scenario is the direct consequence (the widget target has no ChirpKit dependency, so its always-run stamp phase finishes long before the app's own Swift compile)

### R8-8 [medium] [companion/security] — Companion listens on every interface over plain HTTP by default; a "trusted" Mac gets clinical text in clear on any shared network
- Where: `companion/parakeet_companion/config.py:12`; `companion/parakeet_companion/__main__.py:26,191-194`; `companion/README.md:66-67`; `spec/adr/014-mac-companion.md:23-27`; `spec/12-privacy.md:120-128`
- Problem: default bind `0.0.0.0`, plain http, bearer token. The phone judges "home network" and "trusted" by address form (`.local` or a private IP), which hospital and café networks also satisfy (ADR-014 says so and accepts it); the only mitigation is a banner line.
- Failure scenario: MacBook and iPhone both on hospital Wi-Fi, companion still running from home; Listen on a clinical note with "Trusted for clinical text" on → text chunks and the pairing token cross the hospital Wi-Fi unencrypted, with no question asked.
- Fix: cheapest: no `0.0.0.0` default (require `--host`, or bind to the address of the interface named at pairing and refuse to start when it is gone); robust: TLS with a self-signed certificate whose SHA-256 fingerprint is part of the pairing and pinned by the phone.
- Confidence: PLAUSIBLE (design risk, documented and accepted in ADR-014)
