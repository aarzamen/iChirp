# R4 — ChirpFeatures core (pipeline, jobs, deliverables, library)

Reviewer lane R4, repo `/Users/ama/Documents/GitHub/iChirp` at `main` 53bc2cc6. Read-only review; nothing was built or run.

## Overall assessment

The core is careful work: one run per id, a permit-bounded normalization queue, terminal writes outside
cancellation, field-level store writes, routing re-checked before every model call with single-use tokens bound to
the route, honest progress, and an unusually thorough test suite built on signals and fakes rather than sleeps. The
weak points are at the seams. The text that actually reaches the model is the raw ASR word segments, not the cleaned
transcript the person reviewed. A response cut off at the output-token cap is accepted as finished. The system UI and
the run ledger expose or under-report what they should not: file names appear on the Lock Screen, and egress is
under-counted when a run fails. Several clean-up paths handle the normal exit but not a kill (benchmark temp audio,
mid-import folders), and the provider store overwrites unreadable data. `DeliverableService` and the pipeline helpers
duplicate safety logic, and that duplicated logic has already drifted (the edit path).

## Findings (most severe first)

### R4-1 [high] [correctness] Transform and Ask send the raw ASR words, not the cleaned transcript: custom words, snippets, filler removal and "Polish after" never reach the model
- Where: `ChirpKit/Sources/ChirpFeatures/DeliverableService.swift:448`; `ChirpKit/Sources/ChirpText/TranscriptPromptText.swift:14-30`;
  `ChirpKit/Sources/ChirpFeatures/FileTranscriptionPipeline.swift:607-628`;
  `ChirpKit/Sources/ChirpFeatures/Dictation/DictationCoordinator.swift:561-582`; contrast
  `ChirpKit/Sources/ChirpFeatures/Meeting/MeetingFinalizer.swift:249-259`; `ChirpKit/Sources/ChirpFeatures/Create/CreateFlow.swift:450`.
- Problem: `run` builds its source with `TranscriptPromptFormatter.timestampedText`, which returns the segment text
  whenever `transcriptSegments` exist and falls back to `displayText` only when they do not. The file pipeline and
  the dictation final pass both build segments from the raw `result.words`. Custom words, snippets and filler removal
  (Clean, or dictation's "Polish after") are applied only to `cleanTranscript`. Only meetings correct the word tokens
  themselves (`MeetingTranscriptVocabularyApplier`). The M5 plan (`docs/plans/2026-09-22-014-m5-ingest.md:53`) says
  `DeliverableService` reads `displayText`.
- Failure scenario: a dictation with "Polish after" on, a custom word that fixes "metro pull all" to "metoprolol",
  and a snippet that expands "normal cardiac exam" into a full sentence. The Done screen copies the polished text.
  Dictate → SOAP note (Create passes `userNotes: nil`) sends `[00:00] Unknown Speaker: … metro pull all … normal cardiac
  exam`. The note is written from text the clinician never saw, and the snippet's content is missing.
- Fix: apply custom words to word tokens in the file and dictation pipelines (reuse
  `MeetingTranscriptVocabularyApplier`). When cleanup changed the text in ways tokens cannot carry (snippets,
  Polish), send `displayText`, paragraph by paragraph with the nearest segment timestamp. Test in
  `DeliverableServiceTests`: a row with raw words "metro pull all" and a `cleanTranscript` containing "metoprolol"
  and a snippet expansion; assert the request prompt contains both.
- Confidence: CONFIRMED (data path traced end to end).

### R4-2 [high] [correctness / honest UI] Output cut off at the token cap is saved as a complete document
- Where: `ChirpKit/Sources/ChirpFeatures/DeliverableService.swift:596-620` (`send` accepts any `.finished`) and
  `:379-383` (`RunMetrics.add` drops `stopReason`); `ChirpKit/Sources/ChirpFeatures/MapReduceGenerator.swift:176-179`
  (`maxOutputTokens = min(4096, ctx/4)`); `ChirpKit/Sources/ChirpEngineAppleFM/AppleFoundationLanguageModel.swift:53,69`;
  `ChirpKit/Sources/ChirpEngineHTTPLLM/AnthropicLLMHTTPAdapter.swift:56`, `OpenAICompatibleLLMHTTPAdapter.swift:38`;
  contrast `ChirpKit/Sources/ChirpEngineLlamaCpp/LlamaCppEngine.swift:270`.
- Problem: the HTTP engines forward `stop_reason` / `finish_reason` (`max_tokens` / `length`) in
  `GenerationUsage.stopReason`, and `DeliverableService` ignores it. Apple's model, given `maximumResponseTokens`,
  stops early without an error or a stop reason (the documented FoundationModels behaviour). Only the llama.cpp
  engine treats a clinical length stop as a failure (review minor 8), so the guard lives in one engine instead of at
  the one call site.
- Failure scenario: on Apple's model (`contextSize` 4096, so `maxOutputTokens` 1024, about 750 words), meeting notes
  for a one-hour meeting or a long SOAP note stops mid-section and is stored as `.completed`. In the map phase, an
  extract that reaches 1024 tokens silently drops the rest of its part. Both break the "nothing is truncated" rule.
- Fix: read `stopReason` in `send`. On `length` / `max_tokens`, fail the final call with a sentence, and re-plan with
  smaller parts for extract and condense. Have the Apple adapter report `length` when the response reaches the cap.
  Test: a fake model that emits `.usage(stopReason: "length")` then `.finished` stores no deliverable, and the run
  fails or re-plans.
- Confidence: CONFIRMED for the HTTP engines (the stop reason is dropped in code). CONFIRMED by API documentation for
  Apple's model (it ends early with no error).
