# R3 — Engine plug-ins review (iChirp `main` @ 53bc2cc6)

Scope: every `ChirpKit/Sources/ChirpEngine*` target, their tests, `ChirpKit/Package.swift`; specs 06/08, the
speech-engine, language-model, decision-model, structure-model and speech-synthesis contracts, ADR-003/004/010–015.
Read-only review; SDK behaviour was checked against the pinned checkouts in `ChirpKit/.build/checkouts`
(FluidAudio 0.16.1, argmax-oss-swift 1.1.0) and `vendor/NeedleC-headers/needle.h`.

## Overall assessment

The engine layer is careful where earlier reviews looked: FluidAudio's `ModelAssetLifecycle` (leases, generations,
`pendingAcquires`, cancellable shared waits, memory fit before a load), WhisperKit's FIFO permit, the llama.cpp actor
(context budget before decoding, content never tokenized with special tokens, greedy clinical sampling, sticky-error
unload) and the Needle C wrapper (every `char *` freed, thread-local error read in the same synchronous segment) are
sound, and the plug-in rule holds at the SDK level: no file outside an engine target imports FluidAudio, WhisperKit,
FoundationModels, Speech, `llama` or `NeedleC`. Logging is content-free, every HTTP engine uses an ephemeral cache-free
session and refuses redirects, and keys only ever go into headers. The weak spots are about *semantic* completeness and
consistency across siblings: no engine but clinical llama.cpp tells a length-capped answer from a finished one (and
nothing downstream reads `stopReason`), the clinical "faithful sampling" rule exists only in llama.cpp, the Silero VAD
engine sits outside the shared lifecycle and can download silently, and generic helpers were copy-pasted into
several targets and have already drifted (the Needle asset copy lacks fixes its llama.cpp sibling received).

## Findings (most severe first)

### R3-1 [high] [correctness / data integrity] — A generation cut off at the output-token limit is returned, and saved, as a finished document by every engine except clinical llama.cpp
- Where: `ChirpKit/Sources/ChirpEngineHTTPLLM/AnthropicLLMHTTPAdapter.swift:54-71` (`stop_reason` captured, `.finished`
  yielded on `message_stop` whatever it was; `max_tokens` default at :144); `OpenAICompatibleLLMHTTPAdapter.swift:38,55-63`
  (`finish_reason` "length" → `.finished`); `OllamaLLMHTTPAdapter.swift:47-60,121` (`done_reason` "length" → `.finished`,
  `num_predict` = `maxOutputTokens`); `ChirpEngineAppleFM/AppleFoundationLanguageModel.swift:53,66-71`
  (`maximumResponseTokens` cap); `ChirpEngineLlamaCpp/LlamaCppEngine.swift:237-240,270-277` (only a *clinical* length stop
  becomes an error). Consumer: `ChirpFeatures/DeliverableService.swift:596-620` (`send` returns text on `.finished`) and
  :373-384 (`RunMetrics.add` ignores `stopReason`); `GenerationUsage.stopReason` is not read anywhere outside ChirpCore.
- Problem: the language-model contract makes the engine responsible for "is this a whole document" but only checks
  transport sentinels (`message_stop`, `[DONE]`, `done`). A provider length stop is a clean stream end, so a truncated
  text reaches the deliverable store, or a map-reduce note, with nothing marking it incomplete. llama.cpp already
  knows this is not a document (review minor 8 / N3), but only for clinical requests, and the other engines don't.
- Failure scenario: the budget is `min(4096, max(256, window/4))` (`MapReduceGenerator.swift:178`): 1,024 output tokens
  on Apple's model (the default Transform engine) and LAN LM Studio, 2,048 on Ollama's default 8K window. "Polish" of a
  ~1,000-word dictation on the default Apple model needs ~1,400 tokens → generation stops mid-sentence at 1,024 (Apple
  documents that this limit ends the response without an error) → `.finished` → saved as a complete deliverable. Same
  for a clinical Polish or long SOAP note sent to the trusted LAN Ollama (`num_predict` 2,048), the case llama.cpp
  refuses. In map-reduce, an extract or condense note cut at the limit silently drops facts from that part.
- Fix: normalise the stop reason in each adapter (Anthropic `max_tokens`, OpenAI `length`, Ollama `length`) into a
  typed signal (e.g. `GenerationUsage.stoppedAtOutputLimit`, or `LanguageModelError.outputLimitReached`) and have
  `DeliverableService` refuse to store or re-plan with a larger output share. For Apple FM, either leave
  `maximumResponseTokens` nil (an overflow then throws `exceededContextWindowSize` → `contextTooLong` → re-plan) or check
  `tokenCount` on 26.4+. Tests: stub streams ending in `finish_reason:"length"`, `stop_reason:"max_tokens"` and
  `"done_reason":"length"` must surface the signal, and a `DeliverableServiceTests` case must store nothing.
- Confidence: CONFIRMED for the three HTTP adapters, llama.cpp and the consumer; PLAUSIBLE for Apple FM's silent cut
  (framework behaviour per Apple's documentation, not exercised here).

### R3-2 [medium] [privacy / clinical safety] — Clinical requests on Apple FM and trusted LAN servers use random sampling and the server's default repeat penalty, the settings ADR-015 measured to alter doses
- Where: `AppleFoundationLanguageModel.swift:53` (`GenerationOptions(maximumResponseTokens:)` only, so FM's default
  random sampling); `OllamaLLMHTTPAdapter.swift:114-123,160-164` (only `num_ctx` and `num_predict` are sent, so Ollama's
  defaults apply: temperature 0.8, `repeat_penalty` 1.1 over the last 64 tokens); `OpenAICompatibleLLMHTTPAdapter.swift:128-136,218-225`
  (no temperature or penalty fields, so LM Studio's preset defaults apply, including repeat penalty 1.1). Contrast
  `ChirpEngineLlamaCpp/LlamaCppModelCatalog.swift:51-92,136-139` (`faithful` greedy profile for `.clinical`).
- Problem: ADR-015's guardrail and `docs/research/2026-09-22-on-device-llm.md` (2 of 5 SOAP notes lost a dose or turned
  "1 1/2" into "1½" with a token-history penalty; temperature > 0 can draw a different digit) are applied only to
  llama.cpp. Apple FM (on device) and Ollama or LM Studio on a trusted Mac (local network) both receive clinical text
  without an override, but ignore `GenerationRequest.privacyClass` when they choose sampling.
- Failure scenario: a SOAP note on the default Apple model or on the owner's trusted Ollama, with "amoxicillin 500 mg"
  restated in Plan: the repeat penalty lowers the probability of the repeated digits and the plan reads "50 mg", or a
  random draw changes a vital. The draft differs between runs, so Retry is not reproducible.
- Fix: when `request.privacyClass == .clinical`, use FM `GenerationOptions(sampling: .greedy)`; send Ollama
  `options: {temperature: 0, top_k: 1, repeat_penalty: 1.0, presence_penalty: 0, frequency_penalty: 0}`; and for
  OpenAI-compatible LAN servers send `temperature: 0`, `presence_penalty: 0`, `frequency_penalty: 0` (plus
  `repeat_penalty: 1.0`, which llama.cpp and LM Studio servers accept). Tests: request-shape tests assert these fields
  for a clinical request and their absence otherwise; expose FM's option builder for a unit test.
- Confidence: CONFIRMED that no sampling setting is sent or set; impact PLAUSIBLE (it relies on server defaults and
  was measured on llama.cpp).

### R3-3 [medium] [data integrity / contract] — Silero VAD bypasses the shared lifecycle: a partial cache reads Ready, `makeStream` can purge and re-download silently, and the folder is never excluded from backup
- Where: `ChirpEngineFluidAudio/FluidAudioVoiceActivity.swift:43-47` (`isModelCached` = the `.mlmodelc` folder exists),
  :49-53 (`.ready`), :56-67 (download, with no `excludeFromBackup`), :76-87 (`makeStream` → `VadManager(config:modelDirectory:)`).
  SDK: FluidAudio `VAD/VadManager.swift:110-141` → `ModelHub.loadModels` ("handles downloading if needed"), which on a
  non-transient load failure calls `ModelCache.purgeCorruptedCache` and downloads again (`Shared/Download/ModelHub.swift:85-150`).
  `ChirpEngineFluidAudio/README.md:85` says "`makeStream` never downloads".
- Problem: Parakeet and the diarizer use strict completeness (`coremldata.bin`, no `*.partial`, revision marker), load
  from local files only, and exclude their folders from backup. The VAD engine does none of these, contrary to the
  speech-engine contract ("Downloaded folders are marked excluded from backup") and spec/06 ("Using an engine never
  downloads silently"). Its `makeStream` also has an actor-reentrancy double load (`manager == nil` is checked before an
  `await`).
- Failure scenario: a VAD download is interrupted after the bundle folder exists but before `coremldata.bin` lands →
  Settings → Meetings shows Ready → the next meeting start calls `makeStream` → FluidAudio's layout validation throws
  → `loadModels` purges the folder and fetches it from Hugging Face during the meeting start, with no Download tap and
  possibly on cellular. Offline, `makeStream` returns nil (fixed chunks) and the broken folder keeps reading Ready.
- Fix: run VAD through `ModelAssetLifecycle` like the diarizer: strict `incompleteFiles` + `cacheMatchesPinnedRevision`,
  `excludeFromBackup` after download, and a `load` hook that builds the `MLModel` from local files and uses
  `VadManager(config:vadModel:)` (VadManager.swift:103). Test: a cache that has the bundle folder but no
  `coremldata.bin` reads `.notDownloaded`, and `makeStream` returns nil without any `ModelHub` call.
- Confidence: CONFIRMED (traced through FluidAudio 0.16.1).

### R3-4 [medium] [maintainability] — Generic helpers copy-pasted into engine targets have already drifted
- Where: three HTTP transports and three redirect refusers (`ChirpEngineHTTPLLM/LLMHTTPTransport.swift`,
  `ChirpEngineJev/JevHTTPTransport.swift`, `ChirpEngineVoiceHTTP/VoiceHTTPTransport.swift`); three key scrubbers
  (`LLMHTTPErrorMapper.swift:112-126`, `JevHTTPTransport.swift:87-100` + `JevDecisionModel.swift:154-159`,
  `VoiceHTTPTransport.swift:115-131`); two `AsyncPermit.swift` and two `SharedTaskWait.swift`; `MonotonicFraction`
  (`WhisperKitEngine.swift:388-408`) vs `MonotonicProgress` (`AppleSpeechEngine.swift:227-247`); four `excludeFromBackup`
  helpers; two SHA-256 file hashers and two identical URLSession fetchers (llama.cpp and Needle assets).
- Problem: ADR-004 allows duplicating *engine-specific* helpers "guarded by parity tests"; only `WordTimingBuilder` has
  such a test. Observed drift: the scrubbers differ (Voice adds `xai-` and drops `x-api-key:`; Jev and Voice replace the
  literal key, HTTPLLM does not, so a Gemini `AIza…` or Groq `gsk_…` echo would pass); response caps differ (Jev caps
  bodies at 1 MB and messages at 300 characters, while HTTPLLM and Voice `data(for:)` are unbounded and HTTPLLM shows up
  to 64 KB of raw error body); `MonotonicProgress` starts at 0 (never forwards the first 0) and `MonotonicFraction` at
  −1; the Needle asset copy lacks the llama.cpp fixes (R3-5). Jev's README already lists "lift the transport into
  ChirpCore" as a follow-up.
- Fix: move the transport (ephemeral session, redirect refusal, body cap, one scrubber that also replaces the literal
  key), `AsyncPermit`, `awaitSharedTask`, monotonic progress, backup exclusion and a pinned-file downloader (size,
  SHA-256, throttle, cancellation) into ChirpCore (Foundation and CryptoKit only), with one test suite each.
- Confidence: CONFIRMED (diffed).

### R3-5 [low] [correctness] — `NeedleModelAssets` missed the fixes its llama.cpp copy received
- Where: `ChirpEngineNeedle/NeedleModelAssets.swift:146-148` (`record` overwrites, it does not take the max),
  :100-120 (`try await task.value` with no cancellation handler), :123-126 (one unthrottled `Task` per KVO tick),
  :133 (hashing on the actor). Compare `ChirpEngineLlamaCpp/LlamaCppModelAssets.swift:107-114,138-145,155-159`.
- Problem / scenario: progress Tasks arrive out of order, so `assetStatus()` can report `.downloading` going 0.62 →

  task, does not cancel the URLSession fetch inside the unstructured task, so the download continues.
- Fix: port llama.cpp's `max` in `record`, the `withTaskCancellationHandler`, `ProgressThrottle` and off-actor hashing
  (or share the helper from R3-4). Tests: mirror `testCancellingTheCallerStopsTheDownload` and
  `testProgressIsThrottledAndNeverGoesBackwards` for Needle.
- Confidence: CONFIRMED.

### R3-6 [low] [honest UI] — llama.cpp and Needle downloads record a cancellation, or a Delete during a download, as a failure
- Where: `LlamaCppModelAssets.swift:115-118` and :162-165; `NeedleModelAssets.swift:116-119` and :151-153.
- Problem: `catch { failure = …localizedDescription }` also runs for `CancellationError` or `URLError.cancelled`.
  `deleteAssets` clears `failure` before the cancelled download's `catch` runs, so the failure sticks. FluidAudio's
  tracker (`ModelAssetLifecycle.swift:138-142`), WhisperKit (:168) and Apple Speech all treat a cancellation as "not a
  failure".
- Failure scenario: Delete a model mid-download → status `.failed("The operation couldn't be completed.
  (Swift.CancellationError error 1.)")` or `"cancelled"` instead of `.notDownloaded`; the same happens when the
  continued-processing request expires.
- Fix: skip recording on a cancellation (`Task.isCancelled || error is CancellationError || URLError.cancelled`).
  Test: cancel, then assert `.notDownloaded`.
- Confidence: CONFIRMED.

### R3-7 [low] [data integrity / reproducibility] — WhisperKit model and tokenizer come from the moving `main` revision with no hash; the completion marker is written without a completeness check
- Where: `ChirpEngineWhisperKit/LiveWhisperKitBackend.swift:18-28` (`WhisperKit.download(variant:downloadBase:)`
  then `ModelUtilities.loadTokenizer`; argmax 1.1.0 snapshots revision `"main"`, `WhisperKit.swift:250-298`);
  `WhisperKitEngine.swift:148-155` (marker written whenever `backend.download` returns).
- Problem: llama.cpp and Needle weights are pinned by revision, size and SHA-256 (ADR-012, ADR-015); WhisperKit pins
  only the package. A re-upload to `argmaxinc/whisperkit-coreml` or `openai/whisper-*` changes transcripts and makes
  the recorded WER benchmarks stale, with nothing in the app changed. Hub's snapshot also *returns normally* when the
  task is cancelled between files (`HubApi.swift` snapshot loop, `if Task.isCancelled { return repoDestination }`). Today
  the tokenizer fetch that follows also fails on cancellation, so no marker is written, but that ordering is the only
  safeguard: download the tokenizer first, or share one tokenizer between variants, and a partial model would be marked
  complete.
- Fix: download through HubApi with a pinned revision (model and tokenizer), record the resolved commit in the marker
  and show it in the benchmark, and check `Task.checkCancellation()` plus the required files (`AudioEncoder`,
  `TextDecoder`, `MelSpectrogram`, configs) before writing the marker.
- Confidence: CONFIRMED (unpinned); PLAUSIBLE for the marker fragility.

### R3-8 [low] [storage] — WhisperKit Delete never removes the Hub cache in the shared repo folder, where resumable partial downloads live

### R3-9 [low] [concurrency / memory] — WhisperKit can start a new load while `unloadModels()` is still releasing the previous pipeline
- Where: `WhisperKitEngine.swift:254-258` (`pipeline = nil`, then `await loaded.unload()`) and :266-293
  (`loadedPipeline` sees `pipeline == nil` and starts a load).
- Problem: during the suspension, a `transcribe` or `prepare` starts a fresh load. Either the memory check reads memory
  the old pipeline still holds (a spurious `insufficientMemory` for Turbo), or two pipelines briefly coexist.
  README:25 claims "two pipelines are never loaded at once".
- Fix: keep an `unloading: Task` and await it in `loadedPipeline()` before the memory check. Test: a gated
  `unload()` in the fake backend, then a `prepare` that must wait for it.
- Confidence: PLAUSIBLE (narrow window).

### R3-10 [low] [correctness] — Apple FM delta conversion emits text that differs from the model's output, and a test pins it
- Where: `AppleFoundationLanguageModel.swift:130-138`; `Tests/ChirpEngineAppleFMTests/AppleFoundationLanguageModelTests.swift:59-60`.
- Problem: `hasPrefix` and `dropFirst` work on Characters. When a snapshot merges the last grapheme (an emoji modifier,
  a combining mark, a flag) or revises text, the consumer's concatenated deltas no longer equal the snapshot. The test
  asserts `"Hello wor"` → `"Hello there, friend"` gives `"re, friend"`, so the stored text is "Hello worre, friend".
- Scenario: snapshots `"👍"` then `"👍🏽 ok"` → delta `" ok"` → stored `"👍 ok"`; decomposed accents are dropped the same way.
- Fix: diff on `unicodeScalars` (or UTF-8), and when a snapshot is not an extension, fail with `streamingError` rather
  than produce a hybrid. Test: the cases above concatenate to the final snapshot or throw.
- Confidence: CONFIRMED in logic; PLAUSIBLE that FM's string snapshots trigger it.

### R3-11 [low] [privacy, defence in depth] — Jev never checks `DecisionRequest.privacyClass`, though ADR-013 makes "never clinical" absolute

- Problem: only `DecisionService` stands between a clinical transcript and TypeSafe's cloud. Jev has no override path,

- Fix: `guard request.privacyClass != .clinical else { throw LanguageModelError.unavailable(...) }` before encoding.

### R3-13 [low] [correctness / consistency] — Apple Speech: Delete is not refused while a job runs, and Download installs the model even when permission is already denied
- Where: `ChirpEngineAppleSpeech/AppleSpeechEngine.swift:136-142` (releases the reservation with no in-use check);

### R3-14 [low] [contract] — Parakeet words are not normalised to the contract's word invariants, as WhisperKit and Apple Speech are

## Checked and found sound (no finding)
- `Package.swift`: engine SDKs are linked only into their own targets; `Package.resolved` pins FluidAudio 0.16.1 and
  argmax 1.1.0; NeedleC and llama binary targets are added only when `vendor/` exists. The ADR-010 gate is not needed
  for needle-rs or llama.cpp built from source (ADR-012/015), and no Cactus or `libneedle.a` code is present.
- llama.cpp C interop: tokenize and piece buffers resize on negative counts, `INT32_MIN` is handled, batch pointers are
  used only inside `withUnsafeMutableBufferPointer`, the context budget is checked before any decode, the confirming
  decode stays within the window, and `deinit` frees sampler, context and model.
- Needle C interop: argument order matches `needle.h`, returned strings are copied before `needle_free_str`, and
  `needle_last_error` is read in the same synchronous segment.
- HTTP engines: ephemeral session, no cache or cookies, every redirect refused (3xx → `redirectRefused`), keys only
  in headers, error-body collection capped at 64 KB on streams, content-free logs, and Jev's 120 KB request and 1 MB
  response caps.
