# R2 — audio, text pipeline, ingest (ChirpAudio, ChirpText, ChirpIngest)

Commit 53bc2cc6, read-only review.

## Overall assessment

The ported text core is faithful. `WordTimingBuilder`, `SpeakerMerger`, `TranscriptParagraphBuilder`,
`TextProcessingPipeline`, `CustomWordReplacer`, `TranscriptDerivers`, `LiveTranscriptStabilizer` and
`MeetingTranscriptVocabularyApplier` match upstream `bbae9e0e` line for line, and every other port states its changes
in its header (the one unstated change is in R2-9). The audio side is careful work. The normalizer streams with flat
memory, runs on its own queue, deletes its partial file on cancel and is tested on a real multi-track movie. Capture
copies buffers off the render thread and the meeting writer is crash-safe. Logging in all three modules carries only
sizes, statuses and error types. The weak points are at the edges:

- what the language model actually receives as "the transcript" (R2-1);
- network ingest under App Transport Security and its size limits;
- the hand-written ZIP and DOCX readers, which lose clinical symbols and trust declared sizes;
- blocking work that bypasses the project's own "never on the cooperative pool" rule.

Tests are strong for the happy paths. They are thin where it matters clinically: symbols, stereo content, and untrusted
archive and response sizes.

## Findings (most severe first)

### R2-1 [high] [correctness] — Model input for every deliverable prefixes each line with "Unknown Speaker:" and ignores Clean mode and custom words
- Where: `ChirpKit/Sources/ChirpText/TranscriptPromptText.swift:14-30`. The text comes from these sources:
  - the label is set at `ChirpKit/Sources/ChirpText/FileTranscriptSegments.swift:40-44`;
  - segments are built from raw words at `ChirpKit/Sources/ChirpFeatures/FileTranscriptionPipeline.swift:624-627`
    and `ChirpKit/Sources/ChirpFeatures/Dictation/DictationCoordinator.swift:581`;
  - the result is consumed at `ChirpKit/Sources/ChirpFeatures/DeliverableService.swift:448`.
- Problem: `timestampedText(for:)` prefers `transcriptSegments` over `displayText` whenever segments exist. Files,
  dictations, meetings and captions always have segments. That causes two separate problems:
  - **Speaker label.** `FileTranscriptSegments.materialize` labels every segment without a speaker id
    "Unknown Speaker". The formatter prints any non-empty label (`label.isEmpty ? … : "\(stamp) \(label): \(text)"`).
  - **Clean text skipped.** Segment text comes from `wordTimestamps`, which are the engine's raw words. The person's
    Clean mode, custom words, and the dictation's "Polish after" custom words and snippets only reach
    `cleanTranscript`. They never reach the model.
- Failure scenario / evidence: A single-speaker dictation with speaker labels off, and a custom word that fixes a drug
  name. Its SOAP note prompt reads `[00:00] Unknown Speaker: <raw misrecognized drug name> …` on every line. The
  built-in templates then act on that label (`BuiltInTemplates.swift:32` "attribute claims to them", `:55` "List the
  speakers as labeled"). The result is notes that list or quote "Unknown Speaker", built from text the person already
  corrected. The unit test hides the label problem: its no-speaker fixture uses label `""`
  (`ChirpKit/Tests/ChirpTextTests/TranscriptPromptTextTests.swift:19`), a value production never writes.
- Fix:
  - Omit the label when `speakerId == nil`, or when the transcription has no speakers at all.
  - Decide explicitly which text deliverables read. The likely answer is to keep timestamps but take the text from
    `cleanTranscript` when Clean ran, or to apply custom words to the word tokens the way
    `MeetingTranscriptVocabularyApplier` does.
  - Tests: (a) segments made by `FileTranscriptSegments.materialize` with nil speakers give lines with no
    "Unknown Speaker"; (b) a Clean-mode row with a custom word gives prompt text containing the replacement.
- Confidence: CONFIRMED.

### R2-2 [medium] [correctness] — Plain-http media, feed and web links always fail under App Transport Security, with a jargon error
- Where:
  - `ChirpKit/Sources/ChirpIngest/Links/LinkClassifier.swift:135` (http accepted) and `:173-188`;
  - `ChirpKit/Sources/ChirpIngest/Links/MediaDownloader.swift:109`;
  - `ChirpKit/Sources/ChirpIngest/Links/IngestHTTPClient.swift:36-48`;
  - `ChirpKit/Sources/ChirpFeatures/LinkIngestService.swift:511-517`;
  - `App/Info.plist:82-86` and `project.yml:112-113`, where ATS allows only `NSAllowsLocalNetworking`.
- Problem: Everything accepts `http://` URLs, but nothing upgrades them to https and no ATS exception exists. The
  request dies with `URLError.appTransportSecurityRequiresSecureConnection`. `IngestNetworkError.map` has no case for
  that error, so the row shows "The request failed: The resource could not be loaded because the App Transport
  Security policy requires …". Retry repeats the same failure forever.
- Failure scenario / evidence: Two common ways in:
  - **http enclosures.** A podcast whose RSS enclosure or iTunes `episodeUrl` is `http://…mp3` (still common in older
    feeds) fails. `LiveIngestTests.swift:51` already accepts `http` audio URLs as a valid resolution.
  - **Bare hosts.** A pasted bare host such as `cdn.example.com/talk.mp3` becomes `http://…`, because
    `NSDataDetector` adds `http://` before the `https://` fallback at `:183` is reached. That fallback is
    effectively dead code.

  The `.notWeb` message (`:95`) tells people only https works, while http links are classified as actionable.
- Fix:
  - Rewrite `http` to `https` before resolve, probe and download, and in `willPerformHTTPRedirection`.
  - Map `.appTransportSecurityRequiresSecureConnection` to a plain sentence.
  - Run the `https://` fallback before the data detector for bare hosts.
  - Test: the stub sees an `https` request for an `http` enclosure, and the classifier turns a bare-host paste into
    an https URL.
- Confidence: CONFIRMED (code path and ATS configuration). How often real feeds hit it is PLAUSIBLE.

### R2-3 [medium] [safety] — The ZIP reader's "cannot exhaust memory" cap only checks declared sizes; one crafted DOCX inflates without limit
- Where: `ChirpKit/Sources/ChirpIngest/Documents/ZipArchiveReader.swift:6-7` (the claim), `:46-48`, `:69-77`.
- Problem: `maximumEntrySize` is compared with the central directory's *declared* sizes. Then
  `(compressed as NSData).decompressed(using: .zlib)` inflates the entire stream into memory before
  `output.count == entry.uncompressedSize` is checked.
- Failure scenario / evidence: A DOCX of at most 100 MB is accepted (`DocumentTextExtractor.swift:88`). Its
  `word/document.xml` declares 1 KB uncompressed but holds 5 MB of deflated zeros (about 5 GB inflated). It passes
  both caps, then inflates about 5 GB. On an iPhone the app is killed for memory mid-import. The
  `DocumentImportPipeline` row stays processing until the next launch marks it interrupted, and Retry crashes again.
  The README repeats the 128 MB claim.
- Fix: Inflate with `compression_stream` (or `InputFilter`) in chunks, and stop with `.tooLarge` once output exceeds
  `min(entry.uncompressedSize, maximumEntrySize)`. Test: a synthetic entry whose declared size is smaller than its
  real output throws `.tooLarge` or `.damaged`, with bounded memory.
- Confidence: CONFIRMED.

### R2-4 [medium] [safety] — `IngestHTTPClient` enforces `maximumBytes` only after buffering the whole body; the probe's fallback GET can pull a whole video into RAM
- Where: `ChirpKit/Sources/ChirpIngest/Links/IngestHTTPClient.swift:82-98`, `:114-128`.
- Problem: `send` calls `session.data(for:)`, which buffers the full response, then compares its size with
  `maximumBytes`. That covers the 16 MB metadata cap and the probe's "64 KB" cap.
- Failure scenario / evidence: A web link such as `https://host/download?id=7` (no media extension, so it is
  classified `.webLink`) serves a 1.5 GB `video/mp4`.
  - The server answers HEAD with 403 or 405, which signed GET-only URLs and many download scripts do.
  - The fallback `Range: bytes=0-0` GET is ignored and the server sends 200 with the full body.
  - `data(for:)` buffers 1.5 GB before throwing `.tooLarge`, and the app is killed for memory.

  Separately, `MediaDownloader` has no size limit and no free-space check at all.
- Fix:
  - Read with `session.bytes(for:)`, or with a data delegate that cancels once `expectedContentLength` or the running
    total exceeds `maximumBytes`.
  - In `probe`, read the headers and cancel.
  - Test: a stub that ignores Range and streams 10 MB must stop near 64 KB.
- Confidence: CONFIRMED (code). The server combination is PLAUSIBLE.

### R2-5 [medium] [correctness/clinical] — The DOCX reader silently drops symbol characters and duplicates text-box text
- Where: `ChirpKit/Sources/ChirpIngest/Documents/DOCXReader.swift:57-85`.
- Problem: Only `w:t`, `w:tab`, `w:br` and `w:cr` are read.
  - **Dropped characters.** `w:sym` (a character inserted from a symbol font, such as Insert → Symbol with the Symbol
    font) and `w:noBreakHyphen` are ignored.
  - **Doubled text.** Text boxes in Word 2010+ files are written twice, inside `mc:AlternateContent` (`mc:Choice`
    and `mc:Fallback`), so their paragraphs are extracted twice.
- Failure scenario / evidence:
  - A referral letter typed in older Word with symbol-font characters loses them. "K⁺ ≥ 5.5", "SpO₂ ≤ 92 %",
    "37.8 °C" and "± 2" lose the symbol and become "K 5.5" and "SpO2 92 %". "50 µg", where µ is `w:sym` F06D, becomes
    "50 g". A form with a text-box letterhead or field repeats that text.
  - The extracted text feeds SOAP and summary templates and Needle tagging, with no warning that characters were
    dropped.
- Fix:
  - Map `w:sym` (font plus `w:char`) through a small Symbol/Wingdings → Unicode table, or emit "?" and flag the
    document.
  - Emit U+2011 for `w:noBreakHyphen`.
  - Skip everything inside `mc:Fallback`.
  - Add `SyntheticDOCX` cases for each.
- Confidence: CONFIRMED (code). How common these features are in real files is PLAUSIBLE.

### R2-6 [medium] [data integrity] — A dictation write failure (full disk) is silent and logged once per buffer, unlike meetings
- Where: `ChirpKit/Sources/ChirpAudio/Capture/DictationRecorder.swift:162-173`. Compare
  `ChirpKit/Sources/ChirpAudio/Capture/MeetingRecorder.swift:192-205`.
- Problem: `RecordingWriter.process` logs `write_failed` and returns, and does the same for every following buffer.
  It yields no `CaptureEvent.failed` and never stops trying. `MeetingAudioWriter` handles the same situation by
  setting `writeFailed`, emitting one `.failed(message:)` and keeping what was written.
- Failure scenario / evidence: The phone fills up 30 s into a 3-minute clinical dictation. The Dictating screen keeps
  running; only the level meter freezes. At Stop the WAV holds 30 s and the final pass transcribes just that. The
  person copies a truncated note with no warning, and the log gets about 12 `write_failed` lines per second.
- Fix: Mirror `MeetingAudioWriter`: a `writeFailed` flag, a single `.failed(message:)` event and no further writes.
  Test: a writer whose file write fails emits exactly one `.failed` event.
- Confidence: CONFIRMED.

### R2-7 [medium] [concurrency] — Document extraction and voice-message encoding block cooperative-pool threads, and parsing cannot be cancelled
- Where:
  - `ChirpKit/Sources/ChirpIngest/Documents/DocumentTextExtractor.swift:69-102`;
  - `ChirpKit/Sources/ChirpIngest/Documents/PDFTextExtractor.swift:18-59`;
  - called from `ChirpKit/Sources/ChirpFeatures/DocumentImportPipeline.swift:161`;
  - `ChirpKit/Sources/ChirpAudio/VoiceMessage/VoiceMessageWriter.swift:31-35`.
- Problem: These are nonisolated `async` functions in Swift 6 mode with no upcoming features. They run on the global
  concurrent executor and do long synchronous work there:
  - `Data(contentsOf:)` of up to 100 MB;
  - XML, DOCX inflate, Swift `Regex` HTML stripping and `NSAttributedString` RTF parsing;
  - PDF `page.string` and page rendering.

  `VoiceMessageWriter` uses `Task.detached`, which is the same cooperative pool. This contradicts the rule the
  normalizer documents and enforces (`ChirpAudio/README.md`: "a few long imports … would stall every other async
  task"). `DocumentImportPipeline.swift:218` moved the *copy* off the pool, but not the extraction. Non-PDF parsing
  checks for cancellation once, before it starts.
- Failure scenario / evidence: Two large HTML or DOCX imports plus a 300-page text-layer PDF tie up three of the
  iPhone's six pool threads for seconds. Other async work in the app (scheduler hops, store reads, UI tasks awaiting
  results) stalls, and Cancel has no effect until the parse finishes.
- Fix: Run extraction (and `VoiceMessageWriter.write`) through a dispatch-queue bridge like
  `AVAudioNormalizer.runOnDecodeQueue`, mark the entry points `@concurrent`, and check cancellation between blocks
  and pages. Test: same pattern as `testBlockingWorkRunsOnTheDecodeQueue`.
- Confidence: CONFIRMED.

### R2-8 [medium] [correctness/clinical] — Tilde ranges between digits may pair as strikethrough, the same bug class as the fixed "2*3"
- Where: `ChirpKit/Sources/ChirpText/Markdown/MarkdownInline.swift:15-27`, `:45-55`;
  `ChirpKit/Tests/ChirpTextTests/PlainTextFlattenerPropertyTests.swift:97`.
- Problem: `AttributedString(markdown:)` follows GitHub-flavored Markdown, which supports `~` strikethrough.
  `escapeMultiplication` protects only `N*N`. A `~` between two digits can both open and close, so two such ranges on
  one line can pair. This is not one of the known flattener items, and it is outside what the property test checks:
  its tokens contain no `~`, and it compares alphanumeric words only.
- Failure scenario / evidence: A generated plan line "metoprolol 25~50 mg q8~12h" could render with "50 mg q8" struck
  through, and Copy would give "2550 mg q812h". That is a dose corruption pasted into an EMR.
- Fix: Escape `(\d)~(\d)` the way `*` is escaped, add a tilde token to `specialTokens`, and pin both single and
  double tilde behavior in `MarkdownInlineTests`.
- Confidence: PLAUSIBLE. Whether Foundation's parser accepts a single tilde is unverified; a one-line test settles it.

### R2-9 [low] [correctness/port fidelity] — Ogg/Opus/WebM reached through a feed or content type downloads in full, is saved as `.mp3`, then fails with a generic decode error
- Where: `ChirpKit/Sources/ChirpIngest/Links/MediaDownloader.swift:271-294`. Compare upstream
  `Services/PodcastAudioDownloader.swift:156`. Also `PodcastFeedParser.swift:51-53` and `LinkClassifier.swift:111-113`.
- Problem: The classifier refuses `.ogg`, `.opus` and `.webm` only by the *pasted* link's extension. Resolved
  enclosures (the feed parser counts `.ogg`, `.opus` and `.webm` as audio) and `audio/ogg`, `audio/opus` or
  `video/webm` responses pass `isNonMedia`. `fileExtension` dropped upstream's `ogg`/`opus` → `"ogg"` mapping, which
  the header does not state, so these files fall through to `"mp3"`.
- Failure scenario / evidence: The latest episode of an Opus-only feed downloads in full (100 MB or more) as
  `source.mp3`. The normalizer then fails with "Parakeet couldn't read the audio in this file (…)" instead of the
  classifier's clear "can't decode Opus" sentence.
- Fix: Refuse undecodable extensions and MIME types in `prepare`, before any bytes are written. Restore an explicit
  extension mapping for them, or state why it was dropped. Test: a stub returning `audio/ogg` gives
  `.unsupported`/`notMedia` and no file.
- Confidence: CONFIRMED.

### R2-10 [low] [correctness] — The RSS slug fallback matches prefixes in both directions without a word boundary, so it can pick the wrong episode
- Where: `ChirpKit/Sources/ChirpIngest/Links/PodcastEpisodeResolver.swift:161-172`.
- Problem: `candidate.hasPrefix(target) || target.hasPrefix(candidate)` compares raw slugs. `"ep-12-…".hasPrefix("ep-1")`
  is true, and a short feed title such as "Trailer" or "Bonus" is a prefix of many longer slugs.
- Failure scenario / evidence: An episode link older than the newest 200 episodes has a slug that does not exactly
  match its feed title (Apple shortens slugs), in an oldest-first feed. The first feed item titled "Ep 1" matches
  target "ep-12-synthetic-…", and the wrong episode is downloaded and transcribed.
- Fix: Require a `-` boundary (`hasPrefix(x + "-")`). Prefer the longest shared prefix. Never accept a candidate
  shorter than about half the target. Test with "Ep 1" vs "ep-12-x" and "Bonus" vs "bonus-interview-x".
- Confidence: CONFIRMED (logic). The trigger is PLAUSIBLE.

### R2-11 [low] [correctness] — YouTube `LOGIN_REQUIRED` is mapped by the substring "age" and defaults to "robot check", unlike youtube-transcript-api
- Where: `ChirpKit/Sources/ChirpIngest/Links/YouTubeCaptionFetcher.swift:221-228`, with its effect in
  `ChirpKit/Sources/ChirpFeatures/LinkImportViewModel.swift:161-165`.
- Problem:
  - Any `LOGIN_REQUIRED` reason containing the letters "age" (as in "page", "message" or "manage") becomes

  - Every other login reason becomes `.blocked` ("asked for a sign-in or a robot check … Try again later") and *does*

  robot check, and the person is offered a companion fetch that will also fail. The spec says private videos are not
  offered.
- Fix: Match whole reasons as youtube-transcript-api does, and default to `.unplayable(reason)`. Test with the three
  canned reasons.
- Confidence: PLAUSIBLE (depends on YouTube's reason strings).

### R2-12 [low] [data integrity] — Resume accepts any 206 at the right offset without comparing validators, and web-link resumes pin an expiring final URL
- Where: `ChirpKit/Sources/ChirpIngest/Links/MediaDownloader.swift:364-371`, `:230-250`;
  `ChirpKit/Sources/ChirpFeatures/LinkIngestService.swift:161-162`, `:474-481`.
- Problem:
  - **No validator check.** A server that ignores `If-Range` but honors `Range` returns 206 with the *new* file's bytes
    after the file changed. Only `range.start == resumeOffset` is checked, not the 206's ETag or Last-Modified
    against the stored validator.
  - **Expiring URL.** For `.webLink`, the download URL is `probe.finalURL` (after redirects). That URL is stored in
    `download.part.json` and reused by Retry ahead of re-resolving `sourceURL`.
- Failure scenario / evidence:
  - A Frankenstein file: the old prefix plus the new suffix, giving a decode glitch or mismatched audio.
  - A link that redirects to a signed URL with an expiry, cancelled and retried the next day, gets 403 on every Retry
    ("may be private or expired"). Deleting the row is the only way out.
- Fix:
  - Compare the 206's ETag or Last-Modified with the stored values and restart from zero on mismatch.
  - Store and resume the original link.
  - On 401 or 403 with a partial file present, re-resolve once.
- Confidence: CONFIRMED (logic). The servers involved are PLAUSIBLE.

### R2-13 [low] [correctness] — The normalizer silently skips any decoded buffer it cannot copy
- Where: `ChirpKit/Sources/ChirpAudio/AVAudioNormalizer.swift:159-161`, `:247-279`.

  any are dropped.

### R2-14 [low] [tests] — No test proves both channels of a stereo file survive normalization
